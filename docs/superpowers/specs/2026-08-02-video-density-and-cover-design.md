# 视频信息密度与封面产出

日期：2026-08-02
状态：已确认，待实现

## 背景

v1 的五帧视频已能稳定出片（真实 AI + 真实 TTS + 真实渲染，1080×1920 h264+aac）。
从真实成品《认知觉醒》逐帧抽检后，发现三个确定的损失：

1. **大量空屏** —— 按真实比例测算：hook 帧 71% 空、breakdown 帧 72% 空、outro 帧 78% 空。
   竖屏最贵的资源是面积，观众划走的决策在 1-2 秒内完成，空屏等于没说话。
2. **字幕挡正文且被截断** —— 第 40 秒实际渲出「己的大脑」（应为「自己的大脑」）；
   breakdown 帧字幕只剩「态度」两字。原因是 `split_lines` 到 12 字硬切，不看词边界；
   字幕层 `bottom:190` 绝对定位，与 `flex:1` 居中的正文区互不知情，必然重叠。
3. **breakdown 帧零信息增量** —— 实测产出「心智即态度与选择」「科技无法传递心智」，
   都是 quote 原文的同义改写。该帧时长 14.3 秒，正好压在观众决定去留的节点上。

同时，书籍封面已在库中（`Book.cover_path`，`has_cover: true`）却从未被使用，
视频与图文都缺少视觉锚点。

## 目标

- breakdown 帧空白占比降到 15% 以下，且新增信息必须是原文里真实存在的依据
- 字幕不再遮挡正文，不再在词中间截断
- 每帧顶部显示播放进度，让观众知道还剩多久（完播率手段）
- 产出四个平台尺寸的封面图，复用已有文案，不增加 AI 成本

## 非目标

- 不做图文卡片这一整条产物线（与视频是两套产物，混入会让范围失控）
- 不新增「封面标题」AI 字段（等真实数据证明封面带量后再考虑）
- 不改音频链路（TTS / BGM / 字幕时间戳算法均不动）
- 不重排 outro 帧的落款位置（贴底是刻意模仿书的版权页，不是缺陷）

## 决策记录

以下决策均经用户逐项确认：

| 决策点 | 选择 | 理由 |
|---|---|---|
| 版式方案 | **A 撑满 + 进度条** | 空白可压到 15% 以下；副文约束顺带解决同义改写 |
| 封面文案来源 | **A 复用 hook** | 零额外 AI 成本；封面与视频前三秒一致，观众无落差 |
| 副文（evidence）内容 | **A 必须来自原文** | B「允许 AI 展开」等于把零信息增量的毛病用更长文字重犯一遍 |
| evidence 缺失时 | **留空，不编** | 空行是诚实的，会反过来提醒用户划线时多划两句 |
| 进度条含义 | **C 两个都要** | 播放进度（顶部，留客）与读书进度（quote 帧，可信度）解决的问题不同 |
| 封面渲染技术 | **Remotion，非 Pillow** | 复用 `theme.ts` 与字体，版式规则只实现一遍，不会漂移 |

## 真源变更

`backend/schema/frames.py` 是全系统唯一真源。改它意味着 prompt、JSON Schema、
TS 类型、渲染组件、文案生成必须同步跟进 —— 这是既定规矩。

### BreakdownFrame.points

```
现在：list[Text]                    min 2, max 3
改为：list[Point]                   min 2, max 3

class Point(BaseModel):
    text: Text                      max 24    结论
    evidence: Text | None = None     max 40    原文依据
```

`evidence` 用 `str | None` 而**不是**默认空字符串。`None` 表示「这条没有依据」，
渲染时整行不出现；`""` 会渲出空占位而破版。类型上固化这个区别，避免以后有人塞 `""`。

### FramePayload 新增 index / total

```
class FramePayload(CamelModel):
    index: int = Field(ge=0)        # 第几帧，从 0 起
    total: int = Field(gt=0)        # 共几帧
```

放在 `FramePayload` 而非各帧 `data` 内，因为它是**播放位置**信息，不属于内容。
`build_payload` 遍历时天然知道 `i` 与 `len(FRAME_ORDER)`，无需 AI 参与。

### 不变的部分

`QuoteFrame.progress` / `highlighted_at` 保持原样（读书进度留在 quote 帧）；
`Theme` 不变；`Script` 不新增封面字段（封面渲染时直接读 hook 帧数据）。

## evidence 子串校验

**这是本次改动里唯一涉及可信度的部分，必须在代码层兜住。**

Prompt 会明确要求 `evidence` 只能是素材原文里真实出现过的字，可截取、可省略中间，
但不能改写、不能补字；找不到支撑就填 `null`。

但仅靠 prompt 不可靠 —— 与 `HookFrame.check_highlight` 是同一类问题：
交代过，模型仍会自作主张。所以在 `generate_script` 返回前做一次校验：

```
把 evidence 与 source_text 都去掉标点与空白后做子串比对。
不是子串 → 置 None。
```

**假引用比没有引用严重得多**：观众一旦发现引用是编的，账号会失去全部可信度，
而「真读过」正是本产品与洗稿账号唯一的区别。所以取舍是明确的：宁可少一行。

校验放在 `generate_script`（它能同时看到 script 与 `ScriptInput.source_text`），
而不是 `Point` 的 `model_validator` —— 校验器不应依赖其职责之外的数据。

已知代价：AI 好心写的、正确的解释性文字，会因为不在原文里而被丢弃。已接受。

## 视觉层改动

### Shell（所有帧共用，只改一处）

- **顶部进度条**：3px 细线走满整宽，已播部分用 `theme.accent`。
  下方一行小字「<帧名> · 3/5」。新增 `index` / `total` 两个 prop。
- **正文区 `paddingBottom` 约 230px**：这是修字幕挡字的正解。
  现在字幕 `bottom:190` 绝对定位、正文 `flex:1` 居中，两者互不知情所以重叠。
  正文区预留出字幕高度后自然上收。

### Breakdown（重写渲染逻辑）

每条要点从「编号 + 一行字」变为「竖线 + 编号 + 主句 + 副文」。
竖线 2.5px accent 色贯穿整条，把主副两句在视觉上绑成一组。
`evidence` 为 `None` 时不渲染副文 div，竖线随之变短，不留空占位。

要点数量保持 **2-3 条**，不强制 3 条 —— 强制会让 AI 在素材不足时编第三条，
与「宁可留空不编」的原则冲突。

### theme.ts

`point` 字号 46 → 42，新增 `evidence: 30`。这是唯一需要动 theme 的地方。

### 字幕断行

`split_lines` 现在到 12 字硬切。改为优先在词边界断：
在达到 `max_chars` 时，回退到最近的合理断点（标点已处理，需补的是避免切断
连续的中文词组与数字/英文串）。硬上限仍需保留，防止一行过长破版。

### 其余四帧

Hook / Quote / MyTake / Outro 组件本身不改，仅受益于 Shell 的两处改动。

## 封面产出

新增 `backend/core/cover.py`，职责单一：把 hook 数据 + 书信息渲成四个尺寸。

### 四个尺寸

| 比例 | 像素 | 平台 |
|---|---|---|
| 9:16 | 1080×1920 | 抖音 / 视频号 |
| 3:4 | 1080×1440 | 小红书 |
| 1:1 | 1080×1080 | 公众号次条 |
| 2.35:1 | 900×383 | 公众号头条 |

**必须一次性出四个尺寸**：同一张图发四个平台，三个会被裁坏。竖图发公众号头条
被切掉六成，横图发抖音上下补黑边。这不是缩放问题而是排版问题。

### 换行策略

不同尺寸的换行位置必须不同：2.35:1 上「能力不够 只是表象」一行放得下，
9:16 上必须断两行。AI 给的是 `lines` 数组，合并与否由组件按可用宽度决定 ——
2.35:1 时合并成一行，其余保持原数组。

### 实现方式

一个参数化的 Remotion `Composition` + `renderStill()`，四个尺寸在**一次**
Remotion 调用内出完（启动一次 headless Chrome 约 3-5 秒；分四次调用要 12-20 秒）。
参数化优于复制四份组件。

### 产物与接口

- 落位：`storage/jobs/<id>/covers/{9x16,3x4,1x1,2.35x1}.png`，与 `video.mp4` 同级
- `Asset` 表新增 `kind="cover"` 记录，不改表结构（`kind` 本就是自由字符串）
- `GET /api/jobs/{id}/cover/{ratio}`，走已有 `_safe_under` 路径校验
- **`ratio` 必须白名单校验** —— 它进文件路径，绝不能信任

## 验证方式

上一轮 BGM 的教训：手改 `props.json` 只验证了 Remotion 一侧，
真任务里 `resolve_bgm` 的接线从未跑过，结果 `bgmSrc` 一直是 `None`。
所以本次验证一律以**成品**为准，不看中间产物。

1. 改完先跑 `remotion still` 出静帧，肉眼看排版（不必等 TTS 与渲染）
2. 用真实素材跑完整任务，从**成品视频**抽帧检查
3. **实际测量空白占比**（数像素，不靠目测），breakdown 帧目标 < 15%
4. 用一句必然会被切的长句测字幕，确认渲出的字完整、未截断
5. **evidence 校验器单独验证**：喂一段原文极少的素材，
   确认假引用被置 `None` 而不是渲进画面 —— 这条验证的是护城河
6. 四个尺寸封面各自抽检，确认 2.35:1 已合并为一行且文字未被裁切

## 风险

- **Prompt 约束不一定被遵守**（最可能失败的部分）。已用子串校验在代码层兜住，
  最坏情况是 evidence 大量为 `None`、画面比预期略空，但不会出现假引用。
- **进度条是第一个「功能性 UI」元素**，与现有克制风格有张力。已确认采用
  「细线 + 3/5 文字」版；若实测觉得破坏质感，退路是只保留右上角「3/5」文字、不画线。
- **`evidence` 上限 40 字**若定得太紧，会导致原文依据被截断而失去意义。
  实现时若发现频繁触顶，应放宽而不是让 AI 压缩（压缩就成了改写）。
